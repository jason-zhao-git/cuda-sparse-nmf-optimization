% ABSTRACT
\begin{abstract}
\noindent Non-negative Matrix Factorization (NMF) is a cornerstone algorithm in bioinformatics, computer vision, and signal processing. This report presents a comprehensive optimization study of two NMF solvers on NVIDIA A40 GPUs: the \textbf{Multiplicative Update (MU)} and the faster-converging but sequential \textbf{Hierarchical Alternating Least Squares (HALS)}.

We demonstrate that naive parallelization strategies quickly hit hardware limits defined by memory bandwidth and PCIe interconnect latency. To overcome these physical barriers, we introduce two key algorithmic innovations:

\begin{enumerate}
    \item \textbf{Asynchronous Relaxation (MU Level 5):} By synchronizing multi-GPU partial results every 10 iterations instead of every iteration, we reduce PCIe communication by $10\times$, achieving \textbf{1.8$\times$ speedup} over synchronous methods with only 0.004\% error increase.

    \item \textbf{Stochastic Block Parallelism (HALS Level 2):} Using Fisher-Yates shuffling to randomize column update orders, we convert systematic Gauss-Seidel dependencies into random noise, enabling \textbf{690$\times$ speedup} over CPU baseline.
\end{enumerate}

Our results show that effective GPU parallelization requires algorithmic relaxation, not just code optimization.
\end{abstract}

\section{Introduction}

Non-negative Matrix Factorization decomposes a matrix $X \in \mathbb{R}^{m \times n}_{\ge 0}$ into two lower-rank factors:
\begin{equation}
    X \approx WH, \quad W \in \mathbb{R}^{m \times k}, \quad H \in \mathbb{R}^{k \times n}, \quad W, H \ge 0
\end{equation}

The non-negativity constraint produces ``parts-based'' representations where features are additive, leading to greater interpretability than PCA.

\subsection{The Parallelization Dichotomy}

We investigate two algorithms at opposite ends of the parallelization spectrum:

\begin{itemize}
    \item \textbf{Multiplicative Update (MU):} All elements update independently using values from the \textit{previous} iteration (Jacobi-style). Easy to parallelize but converges slowly ($\sim$100-200 iterations).

    \item \textbf{HALS:} Updates columns sequentially, with each column using \textit{current} values from previously-updated columns (Gauss-Seidel). Converges fast ($\sim$50 iterations) but inherently sequential.
\end{itemize}

\subsection{Hardware Platform}

All experiments were conducted on the University of Michigan Lighthouse cluster using 2$\times$ NVIDIA A40 GPUs. Notably, the GPUs are connected through the CPU (no direct NVLink), which impacts multi-GPU communication performance.

% ==================================================
% 2. MATHEMATICAL FOUNDATION
% ==================================================
\section{Mathematical Foundation}

Given an input matrix $X \in \mathbb{R}^{m \times n}_{\ge 0}$ with $m$ features and $n$ samples, NMF seeks a low-rank approximation $X \approx WH$ where $W \in \mathbb{R}^{m \times k}$ is the \textit{basis matrix} containing $k$ latent factors, and $H \in \mathbb{R}^{k \times n}$ is the \textit{coefficient matrix} encoding how each sample combines these factors. The factorization rank $k$ is typically much smaller than both $m$ and $n$ (in our experiments, $k = 20$).

\subsection{MU Update Rules}
The multiplicative update rules preserve non-negativity automatically:
\begin{align}
    H &\leftarrow H \odot \frac{W^T X}{W^T W H + \epsilon} \\
    W &\leftarrow W \odot \frac{X H^T}{W H H^T + \epsilon}
\end{align}
where $\odot$ denotes element-wise multiplication, division is element-wise, and $\epsilon = 10^{-10}$.

\textbf{Computational Cost per Iteration:}
Each MU iteration requires several matrix operations of varying computational cost. The dominant operations are the large GEMM products $W^T X$ and $X H^T$, each requiring $O(kmn)$ FLOPs. The smaller products $W^T W$ ($O(k^2 m)$ FLOPs) and $H H^T$ ($O(k^2 n)$ FLOPs) are relatively inexpensive since $k \ll m, n$, and can be cached and reused. The final element-wise updates contribute only $O(kn)$ and $O(km)$ FLOPs respectively. In total, one iteration costs approximately $4kmn + 4k^2m + 4k^2n$ FLOPs, dominated by the $O(kmn)$ GEMM operations when processing large matrices.

\subsection{HALS Update Rules}
For feature $f = 0, 1, \ldots, k-1$:
\begin{equation}
    W_{:f} \leftarrow \max \left( \epsilon, W_{:f} + \frac{[X H^T]_{:f} - \sum_{l=0}^{k-1} W_{:l} [H H^T]_{lf}}{[H H^T]_{ff}} \right)
\end{equation}

\textbf{The Sequential Dependency:} When updating column $f$, the summation term uses:
\begin{itemize}
    \item Columns $0, 1, \ldots, f-1$: \textbf{Updated} values (from current iteration)
    \item Columns $f+1, \ldots, k-1$: \textbf{Old} values (from previous iteration)
\end{itemize}

This Gauss-Seidel ordering accelerates convergence but creates a strict dependency chain that resists parallelization.

\section{Part I: Singel GPU Multiplicative Update Optimization}

\subsection{Level 1: Custom Naive GEMM}

Our baseline implements naive matrix multiplication where each CUDA thread computes one output element:

\begin{algorithm}[H]
\caption{Naive GEMM Kernel (Level 1)}
\begin{algorithmic}
\STATE \textbf{Input:} $A \in \mathbb{R}^{M \times K}$, $B \in \mathbb{R}^{K \times N}$
\STATE \textbf{Output:} $C \in \mathbb{R}^{M \times N}$ where $C = A \times B$
\STATE
\STATE Thread$(i, j)$ computes:
\STATE $\quad C_{ij} \leftarrow 0$
\FOR{$p = 0$ to $K-1$}
    \STATE $C_{ij} \leftarrow C_{ij} + A_{ip} \cdot B_{pj}$ \COMMENT{2 global loads per iteration}
\ENDFOR
\STATE Store $C_{ij}$ to global memory
\end{algorithmic}
\end{algorithm}

Each thread performs $2K$ global memory reads with $\sim$400 cycle latency each. Adjacent threads redundantly load the same row of $A$, wasting a lot of bandwidth.

\subsection{Level 2-3: cuBLAS with ILP Element-wise Optimization}

We replaced custom GEMM with NVIDIA's cuBLAS library (Level 2) and added 8-way instruction-level parallelism to element-wise kernels (Level 3):

\noindent
\begin{minipage}[t]{0.48\textwidth}
\begin{algorithm}[H]
\caption{L2: cuBLAS + Fused Kernel}
\begin{algorithmic}
\STATE \textbf{// H Update}
\STATE $\text{WtW} \leftarrow \texttt{cublasSgemm}(W^T, W)$
\STATE $\text{WtX} \leftarrow \texttt{cublasSgemm}(W^T, X)$
\STATE $\text{Denom} \leftarrow \texttt{cublasSgemm}(\text{WtW}, H)$
\STATE \textbf{Fused:} $H \leftarrow H \odot \text{WtX} / \text{Denom}$
\STATE \textbf{// W Update (symmetric)}
\end{algorithmic}
\end{algorithm}
\end{minipage}
\hfill
\begin{minipage}[t]{0.48\textwidth}
\begin{algorithm}[H]
\caption{L3: cuBLAS + 8-way ILP Kernel}
\begin{algorithmic}
\STATE Thread $t$ processes $[8t, 8t+7]$:
\STATE \textbf{Phase 1:} Issue 24 loads
\FOR{$i = 0$ to $7$}
    \STATE $h_i, n_i, d_i \leftarrow$ load arrays
\ENDFOR
\STATE \textbf{Phase 2:} Compute (overlapped)
\STATE \textbf{Phase 3:} Store 8 results
\end{algorithmic}
\end{algorithm}
\end{minipage}

\vspace{0.5em}
cuBLAS leverages shared memory tiling and auto-tuned kernels. The ILP optimization hides memory latency by issuing multiple independent loads before computation.

% ==================================================
\section{Part II: Multi-GPU Data Parallelism}

\subsection{Data Partitioning and Communication Strategy}

Scaling MU to multiple GPUs requires partitioning the matrices across devices while minimizing inter-GPU communication. The key challenge is that both the H and W updates involve matrix products that combine information from the full dataset---na\"ively, this would require expensive AllReduce operations after every computation.

We chose \textbf{column-wise partitioning} of $X$ and $H$, with $W$ \textbf{replicated} on all GPUs:

\begin{equation}
\begin{aligned}
    \text{GPU 0:} & \quad X[:, 0:n/2], \quad H[:, 0:n/2], \quad W \text{ (full copy)} \\
    \text{GPU 1:} & \quad X[:, n/2:n], \quad H[:, n/2:n], \quad W \text{ (full copy)}
\end{aligned}
\end{equation}

The choice between column-wise and row-wise partitioning determines which update requires inter-GPU communication. With column-wise partitioning, the H update can proceed entirely locally since each GPU has all it needs: $H_{\text{local}} \leftarrow H_{\text{local}} \odot (W^T X_{\text{local}}) / (W^T W H_{\text{local}})$. The W update, however, requires combining partial results across GPUs.

\begin{table}[h]
\centering
\caption{Communication Analysis: Column vs Row Partitioning}
\begin{tabular}{@{}lcc@{}}
\toprule
& Column-wise (Our Choice) & Row-wise (Alternative) \\ \midrule
H Update & \textbf{No communication} & AllReduce $W^T X$ ($k \times n$) \\
W Update & AllReduce $XH^T$ ($m \times k$) & \textbf{No communication} \\
Comm Size & $k(k + m)$ floats & $k(k + n)$ floats \\ \bottomrule
\end{tabular}
\end{table}

For $m = n$, both partitioning strategies are equivalent in communication cost. But column-wise is more natural for ML workloads where $n$ (samples) often exceeds $m$ (features), and partitioning by samples is the standard data-parallel pattern. We replicate $W$ rather than partitioning it for three reasons:

\begin{enumerate}
    \item \textbf{H update needs full W:} Computing $W^T \times X_{\text{local}}$ requires all rows of $W$
    \item \textbf{W is small:} Only $m \times k$ elements (with $k=20$, this is negligible)
    \item \textbf{Avoids broadcast after W update:} All GPUs compute identical W updates redundantly
\end{enumerate}

\textbf{Per-iteration data movement for W update:}

Each GPU must transfer two matrices to the CPU for the AllReduce operation:
\begin{itemize}
    \item $HH^T$: $k \times k$ floats (for $k=20$: just 400 floats = 1.6 KB)
    \item $XH^T$: $m \times k$ floats (for $m=32000, k=20$: 640,000 floats = 2.56 MB)
\end{itemize}

The AllReduce involves:
\begin{enumerate}
    \item \textbf{Device-to-Host:} Each GPU copies local $HH^T$ and $XH^T$ to pinned CPU memory
    \item \textbf{CPU Reduction:} Sum all partial contributions on CPU
    \item \textbf{Host-to-Device:} Broadcast global results back to all GPUs
\end{enumerate}

While we did not profile the exact transfer times, the empirical results (Table~\ref{tab:l4fail}) show that the communication overhead from 100 AllReduce operations per run exceeded any compute savings from parallelization.

\subsection{From Synchronous Failure to Asynchronous Innovation}

Our initial multi-GPU implementation (Level 4) followed the textbook approach: after each iteration, all GPUs synchronize their partial results via AllReduce before proceeding to the next iteration. This guarantees mathematical equivalence to the single-GPU algorithm. However, the results were disappointing---two GPUs were consistently \textit{slower} than one:

\begin{table}[h]
\centering
\caption{Level 4 Synchronous Multi-GPU: 2 GPUs Slower Than 1}
\label{tab:l4fail}
\begin{tabular}{@{}rcccc@{}}
\toprule

\end{tabular}
\end{table}

The root cause is hardware topology. Running \texttt{nvidia-smi topo -m} reveals that our A40 GPUs connect through the CPU via PCIe, not through direct NVLink. Each AllReduce requires data to travel GPU$\to$CPU$\to$GPU, and with 100 iterations, we perform 100 such round-trips. The communication overhead exceeds any compute savings from parallelization. Even at the largest matrix size (32,000), where compute time is substantial, synchronous multi-GPU achieves only 0.88$\times$ the single-GPU speed.

\textbf{The Key Insight: MU is Self-Correcting.} Unlike algorithms that require exact intermediate values, the Multiplicative Update rule is inherently robust to small perturbations. Each iteration moves $W$ and $H$ closer to a fixed point, and small errors in one iteration are naturally corrected in subsequent iterations. This property---unique to the multiplicative update formulation---opens the door to \textit{asynchronous relaxation}: what if we synchronize less frequently and tolerate temporarily stale values?

We introduce Level 5, an asynchronous multi-GPU algorithm tailored specifically to exploit MU's self-correcting nature:

\begin{algorithm}[H]
\caption{Level 5: Asynchronous Multi-GPU MU (Our Innovation)}
\begin{algorithmic}
\STATE \textbf{Input:} Sync interval $\tau$ (we test $\tau = 5, 10$)
\FOR{iteration $t = 1$ to $T$}
    \STATE \textbf{H Update:} Each GPU updates local $H_g$ independently (no communication)
    \STATE \textbf{W Prep:} Each GPU computes $A_{\text{loc}} = H_g H_g^T$, $B_{\text{loc}} = X_g H_g^T$
    \IF{$t \mod \tau == 0$}
        \STATE $A_{\text{global}} \leftarrow \sum_g A_{\text{loc|}g}$, $B_{\text{global}} \leftarrow \sum_g B_{\text{loc|}g}$ \COMMENT{AllReduce via CPU}
    \ELSE
        \STATE $A_{\text{global}} \approx 2 \cdot A_{\text{loc}}$, $B_{\text{global}} \approx 2 \cdot B_{\text{loc}}$ \COMMENT{Local approx, no comm}
    \ENDIF
    \STATE \textbf{W Update:} All GPUs update $W$ using $A_{\text{global}}$, $B_{\text{global}}$
\ENDFOR
\end{algorithmic}
\end{algorithm}

The algorithm reduces communication by a factor of $\tau$: with $\tau = 10$, we perform only 10 AllReduce operations instead of 100, a 10$\times$ reduction in PCIe traffic. Between sync points, each GPU uses a scaled version of its local partial products as an approximation to the global sum. This approximation introduces small errors, but MU's iterative nature corrects them at the next sync point.

The results validate our approach. At small sizes, communication still dominates and even async multi-GPU cannot beat single-GPU. But as matrix size grows, the compute-to-communication ratio improves: at size 8,000, async multi-GPU finally surpasses single-GPU (1.12$\times$), and at size 32,000, we achieve 1.55$\times$ speedup over single-GPU and 1.76$\times$ over synchronous multi-GPU. Crucially, the error impact is negligible---at most 0.76\% at small sizes, dropping to just 0.004\% at large sizes where the local approximation better represents the global structure.

This asynchronous relaxation strategy is specifically tailored to MU's mathematical properties. Algorithms that require exact intermediate values for correctness or convergence guarantees cannot safely skip synchronization. MU's gradient descent like step-wise, self-correcting updates make it uniquely suitable to this kind of optimization.

% ==================================================
\section{Part III: HALS -- Parallelizing the Unparallelizable}

The MU algorithm solves a non-convex optimization problem with no guarantee of reaching the global optimum. This property works in our favor: since each update is already an approximation, we can tolerate stale values and asynchronous communication without significantly affecting convergence. HALS presents an entirely different challenge---it is inherently a \textit{CPU algorithm}, designed around sequential memory access patterns and Gauss-Seidel iteration that assumes immediate availability of updated values. It is the hardest parallelization problem in this project because the algorithm's faster convergence depends critically on this sequential ordering.

\subsection{The Sequential Dependency Problem}

Recall the HALS update rule for column $f$ of $W$:
\begin{equation}
W_{:,f} \leftarrow \max\left(\epsilon, \frac{[XH^T]_{:,f} - \sum_{l \neq f} W_{:,l} [HH^T]_{l,f}}{[HH^T]_{f,f}}\right)
\end{equation}

The critical term is $\sum_{l \neq f} W_{:,l} [HH^T]_{l,f}$, which computes the interaction between column $f$ and all other columns. In HALS, when updating column $f$, we use the \textit{already-updated} values of columns $0, 1, \ldots, f-1$ from the current iteration, and the \textit{old} values of columns $f+1, \ldots, k-1$ from the previous iteration. This is Gauss-Seidel iteration: each update immediately incorporates the latest information, enabling faster convergence than Jacobi-style methods (like MU) that use entirely stale values.

The price of this faster convergence is a strict sequential dependency: column $f$ cannot begin updating until column $f-1$ has finished. With $k=20$ factors, we have a chain of 20 dependent operations per matrix per iteration. Na\"ively, this seems impossible to parallelize.

\subsection{Level 1: Strict Parallelism Within Columns}

Our first GPU implementation preserves the exact Gauss-Seidel ordering while parallelizing \textit{within} each column update:

\begin{algorithm}[H]
\caption{HALS GPU Strict: Preserve Sequential Ordering}
\begin{algorithmic}
\STATE \textbf{Precompute on GPU:}
\STATE \quad $\text{Num} \leftarrow XH^T$ \quad ($m \times k$ matrix, via cuBLAS)
\STATE \quad $\text{Denom} \leftarrow HH^T$ \quad ($k \times k$ matrix, via cuBLAS)
\STATE
\FOR{$f = 0$ to $k-1$}
    \STATE \textbf{Kernel 1 -- Update column $f$} with $m$ parallel threads:
    \STATE \quad \textbf{for} $i = 0$ to $m-1$ \textbf{in parallel do}
    \STATE \quad \quad $\text{interaction} \leftarrow \sum_{l=0}^{k-1} W_{i,l} \cdot \text{Denom}_{l,f}$
    \STATE \quad \quad $W_{i,f} \leftarrow W_{i,f} + (\text{Num}_{i,f} - \text{interaction}) / \text{Denom}_{f,f}$
    \STATE \quad \quad $W_{i,f} \leftarrow \max(\epsilon, W_{i,f})$
    \STATE \textbf{Synchronize} (must complete before column $f+1$)
    \STATE
    \STATE \textbf{Kernel 2 -- Normalize column $f$:}
    \STATE \quad Compute $\|W_{:,f}\|_2$ via parallel reduction
    \STATE \quad $W_{:,f} \leftarrow W_{:,f} / \|W_{:,f}\|_2$
    \STATE \textbf{Synchronize}
\ENDFOR
\end{algorithmic}
\end{algorithm}

This approach launches $m$ threads to update all rows of column $f$ simultaneously---a significant speedup over CPU where rows are processed sequentially. However, it incurs substantial overhead: for $k=20$, we launch 60 kernels per iteration (20 updates + 20 normalizations for both $W$ and $H$), each with $\sim$5-10 $\mu$s launch latency. The GPU spends considerable time waiting for synchronization rather than computing.

\subsection{Level 2: Breaking the Dependency with Stochastic Block Parallelism}

Can we update multiple columns simultaneously without destroying convergence? The na\"ive approach---simply processing all $k$ columns in parallel---degrades to Jacobi iteration, losing HALS's convergence advantage. We experimented with a middle ground: \textbf{block-parallel} updates where columns are grouped into blocks, with parallelism \textit{between} blocks and sequential ordering \textit{within} blocks.

\textbf{The Problem with Fixed Blocks.} If we always group columns $\{0,1,2,3,4\}$ into Block 0, a systematic bias emerges: column 0 \textit{never} sees the updated value of column 4 within the same iteration, while column 4 \textit{always} uses stale values from columns 5-19. Over many iterations, this creates persistent errors that degrade final reconstruction quality.

\textbf{Our Innovation: Fisher-Yates Shuffling.} We break the systematic bias by randomly permuting the column order each iteration using Fisher-Yates shuffling. If column 3 and column 17 happen to be in the same block this iteration, they will likely be in different blocks next iteration. Over many iterations, every pair of columns experiences both orderings (updated-before and updated-after), and the errors average to zero.

\begin{algorithm}[H]
\caption{HALS GPU Block: Stochastic Parallelism (Our Innovation)}
\begin{algorithmic}
\STATE \textbf{Initialize:} Create $k/b$ CUDA streams $\{s_0, s_1, \ldots, s_{k/b-1}\}$
\STATE
\FOR{iteration $t = 1$ to $T$}
    \STATE \textbf{Precompute:} $\text{Num} \leftarrow XH^T$, $\text{Denom} \leftarrow HH^T$ (via cuBLAS)
    \STATE
    \STATE \textbf{Shuffle column order:} $\pi \leftarrow \text{FisherYatesShuffle}(\{0, 1, \ldots, k-1\}, \text{seed}=t)$
    \STATE \textbf{Partition into blocks:} $\mathcal{B}_i = \{\pi_{i \cdot b}, \pi_{i \cdot b + 1}, \ldots, \pi_{(i+1) \cdot b - 1}\}$
    \STATE
    \STATE \textbf{for} each block $\mathcal{B}_i$ \textbf{in parallel} on stream $s_i$ \textbf{do}
    \STATE \quad \textbf{for} each column $f \in \mathcal{B}_i$ \textbf{sequentially do}
    \STATE \quad \quad Launch update kernel for column $f$:
    \STATE \quad \quad \quad \textbf{for} $j = 0$ to $m-1$ \textbf{in parallel do}
    \STATE \quad \quad \quad \quad $\text{interaction} \leftarrow \sum_{l=0}^{k-1} W_{j,l} \cdot \text{Denom}_{l,f}$
    \STATE \quad \quad \quad \quad $W_{j,f} \leftarrow \max(\epsilon, W_{j,f} + (\text{Num}_{j,f} - \text{interaction}) / \text{Denom}_{f,f})$
    \STATE \quad \quad Launch normalize kernel for column $f$
    \STATE
    \STATE \textbf{Synchronize all streams} (single barrier per iteration)
\ENDFOR
\end{algorithmic}
\end{algorithm}

\textbf{Block Size Trade-off.} The block size $b$ controls the parallelism-convergence trade-off:

\begin{table}[h]
\centering
\caption{Block Size Analysis ($k=20$): Parallelism vs Convergence Quality}
\begin{tabular}{@{}cccl@{}}
\toprule
Block Size & Num Blocks & Syncs/Iter & Convergence \\ \midrule
1 & 20 & 60 & Perfect (= Strict, no parallelism) \\
5 & 4 & 2 & Good (\textbf{chosen}: 4-way parallelism) \\
10 & 2 & 2 & Degraded (too much stale data) \\
20 & 1 & 2 & Poor (= full Jacobi) \\ \bottomrule
\end{tabular}

We chose $b=5$, which provides 4-way parallelism (4 CUDA streams executing concurrently) while maintaining Gauss-Seidel ordering within each block. This reduces synchronization from 60 barriers per iteration to just 2, a 30$\times$ reduction in sync overhead.

The speedups are dramatic: at size 32,000, both GPU implementations achieve nearly \textbf{700$\times$} speedup over CPU---transforming a 9-minute computation into just over 800 milliseconds. The Block variant consistently outperforms Strict by 3-10\% due to reduced synchronization overhead (2 barriers vs 60 per iteration).

\textbf{Why Such Massive Speedups?} The CPU processes rows sequentially within each column, requiring $O(m)$ time per column update. The GPU parallelizes all $m$ rows simultaneously, reducing this to $O(1)$ parallel time (plus kernel launch overhead). As $m$ grows, the GPU's advantage compounds: at $m=32,000$, we parallelize 32,000 independent row operations per column, and the kernel launch overhead becomes negligible relative to the computation.

\textbf{The Error-Speed Trade-off.} The Block variant achieves higher speedup but at a cost: reconstruction error increases from 0.040 (Strict) to 0.098 (Block) at size 32,000. This $\sim$2.5$\times$ error increase is the price of breaking Gauss-Seidel dependencies---some column pairs inevitably use stale values. However, the Fisher-Yates shuffling prevents this error from accumulating systematically, and for many applications (topic modeling, image decomposition, recommender systems), this error level remains acceptable. The choice between Strict and Block depends on the application's tolerance for approximation versus its need for speed.

The roofline analysis confirms efficient hardware utilization: at size 32,000, GPU Strict achieves 10,097 GFLOPS (27\% of peak compute) and 265 GB/s memory bandwidth (38\% of peak), indicating a balanced workload that effectively saturates both compute and memory subsystems.

% 7. WHAT DIDN'T WORK
% ==================================================
\section{Lessons Learned: What Didn't Work}

Not all optimizations succeeded. Our synchronous multi-GPU (Level 4) ran \textit{slower} than a single GPU---PCIe latency exceeded compute savings. Our ILP optimization provided zero improvement because GEMM dominated runtime, making element-wise optimizations irrelevant by Amdahl's Law. For HALS, block-parallel without shuffling created systematic bias that degraded convergence, and setting block size to $k$ (full parallelism) reduced HALS to Jacobi-style iteration.

The common theme: \textit{na\"ive parallelization either hits hardware limits or destroys algorithmic properties}. Success required understanding both hardware constraints and mathematical nature of the problem.

% ==================================================
% 8. CONCLUSION
% ==================================================
\section{Conclusion}

This project reinforced a fundamental lesson: \textit{the bottleneck is rarely where you expect}. Textbook optimizations---tiled GEMM, ILP, data-parallel multi-GPU---fell short because real performance depends on factors outside complexity analysis: library overhead, PCIe topology, and the interaction between algorithmic structure and hardware.

The key insight was that effective parallelization requires \textit{algorithmic relaxation}, not just code optimization. For MU, we exploited tolerance for stale values to reduce synchronization. For HALS, we used randomization to convert systematic Gauss-Seidel dependencies into manageable noise. Both innovations required understanding \textit{why} these algorithms work---what perturbations they tolerate---before knowing \textit{how} to parallelize them safely.

The takeaway: profile before optimizing, check hardware topology before scaling, and always ask whether an algorithm's mathematical structure permits your intended parallelization. The fastest code respects both the hardware and the mathematics.
